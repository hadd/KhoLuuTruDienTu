# i18n Rules (Multi-Namespace Implementation)

Kết hợp sự linh hoạt của JSON với sự chặt chẽ của TypeScript, sử dụng cấu trúc multi-namespace để tổ chức translations theo domain.

## Structure

- **Locales Structure**: `src/lib/i18n/locales/{lang}/{namespace}.json`
- **Namespaces**: `common`, `auth`, `home` (add more as needed)
- **Languages**: `en` (fallback), `vi` (default)
- **Config**: `src/lib/i18n/config.ts`
- **Type Declaration**: `src/types/i18next.d.ts`

## Adding New Translations

**Step-by-step process:**

1. **Add key to English namespace first**:
   - Edit `src/lib/i18n/locales/en/{namespace}.json`
   - Add the new key (e.g., `"newKey": "New Text"`)

2. **Add corresponding translation**:
   - Edit `src/lib/i18n/locales/vi/{namespace}.json`
   - Add the same key with Vietnamese translation

3. **If adding a new namespace**:
   - Create `src/lib/i18n/locales/en/{newNamespace}.json`
   - Create `src/lib/i18n/locales/vi/{newNamespace}.json`
   - Update `src/lib/i18n/config.ts` to import and register the new namespace
   - Update `src/types/i18next.d.ts` to include the new namespace in type definitions

## Usage in Components

```typescript
import { useTranslation } from 'react-i18next'

function MyComponent() {
  const { t } = useTranslation('auth') // Specify namespace
  
  return (
    <div>
      <h1>{t('title')}</h1>
      <p>{t('benefits.manageClasses')}</p> {/* Nested keys */}
    </div>
  )
}
```

## Rules

- **NEVER hardcode text strings** - Always use translation keys
- Always add keys to `en/{namespace}.json` first, then `vi/{namespace}.json`
- TypeScript will catch invalid keys via type definitions
- Default language is `vi`, fallback is `en`, default namespace is `common`
- **Namespace Selection**: Always specify namespace when calling `useTranslation('namespace')`
- **Nested Keys**: Use dot notation for nested keys: `t('benefits.manageClasses')`
- **Language Detection**: Use `useCurrentLanguage()` hook from `@/lib/hooks/useCurrentLanguage` 
- **Type Safety**: TypeScript will automatically check valid keys via `i18next.d.ts`

## Convention-over-Configuration: Namespace Selection

**Principle**: Feature folder name determines namespace name.

**Formula**: `features/{feature-name}/` → `useTranslation('{feature-name}')`

AI MUST derive the namespace automatically from the feature folder path:
- Take the folder name under `features/`
- Use it directly as the namespace name
- No lookup table needed - convention is universal

**Examples** (for illustration only):
- `features/students/` → `useTranslation('students')`
- `features/academic-years/` → `useTranslation('academic-years')`
- `features/question-studio/` → `useTranslation('question-studio')`

**Exception Rule**: If a component renders entities from a different domain, use that entity's namespace.
```typescript
// In features/school-management/ rendering student data:
const { t } = useTranslation('students') // Use entity's namespace, not 'school-management'
```

## Abstract Key Structure Pattern

**Formula**: `{context}.{group}.{element}.{modifier}`

Keys follow a hierarchical, context-based structure:

```
┌─────────────────────────────────────────────────────────────┐
│  {context}     │  {group}    │  {element}   │  {modifier}   │
├─────────────────────────────────────────────────────────────┤
│  table         │  columns    │  name        │  -            │
│  form          │  fields     │  email       │  label        │
│  form          │  fields     │  email       │  placeholder │
│  form          │  actions    │  submit      │  -            │
│  form          │  success    │  create      │  -            │
│  delete        │  -          │  confirmTitle│  -            │
│  status        │  -          │  active      │  -            │
└─────────────────────────────────────────────────────────────┘
```

**Standard Contexts** (AI must use these):

| Context | Purpose | Required Groups |
|---------|---------|-----------------|
| `table` | Table/list display | `columns.*` |
| `form` | Create/edit forms | `fields.*.label`, `fields.*.placeholder`, `actions.*`, `success.*` |
| `delete` | Delete confirmation | `confirmTitle`, `confirmDescription`, `confirmButton`, `cancelButton` |
| `filter` | Filter UI | `title`, `button`, `clear`, `apply` |
| `status` | Status values | Direct keys: `active`, `inactive`, etc. |
| `actions` | Action buttons | Direct keys: `view`, `edit`, `delete` |
| `errors` | Error messages | Direct keys: `loadFailed`, `notFound` |

**Key Naming Rules**:
- Use `columns` for table headers: `table.columns.name` (not `table.name`)
- Use `fields.{field}.label/placeholder` for form fields: `form.fields.email.label` (not `form.email`)
- Use `confirmTitle/confirmDescription` for dialogs: `delete.confirmTitle` (not `delete.title`)
- Use `success/error` for toast messages: `form.success.create` (not `createSuccess`)
- Status values under `status.*`: `status.active` (not `activeStatus`)

## Standard Namespace Template

Every namespace file MUST include these root-level keys. AI MUST use this template when creating new namespaces:

```json
{
  "title": "{Feature Title}",
  "empty": "No {items} found",
  "search": {
    "placeholder": "Search {items}..."
  },
  "table": {
    "columns": {
      /* column headers */
    }
  },
  "form": {
    "fields": {
      /* field labels and placeholders */
    },
    "actions": {
      "cancel": "Cancel",
      "create": "Create",
      "update": "Update",
      "saving": "Saving..."
    },
    "success": {
      "create": "{Entity} created successfully",
      "update": "{Entity} updated successfully"
    }
  },
  "delete": {
    "confirmTitle": "Delete {Entity}",
    "confirmDescription": "Are you sure you want to delete this {entity}?",
    "confirmButton": "Delete",
    "cancelButton": "Cancel",
    "success": "{Entity} deleted successfully",
    "error": "Failed to delete {entity}"
  },
  "status": {
    /* status values */
  },
  "actions": {
    /* action labels */
  },
  "errors": {
    /* error messages */
  }
}
```

## Namespace Size Management

**Rule**: No namespace file should exceed 200 lines. When approaching this limit:

1. **Split by feature domain**: Create separate namespace files for each feature
   - Keep related keys together (e.g., `students.form`, `students.table`, `students.status`)

2. **Naming convention**: Use feature folder name as namespace (matches convention above)

3. **Common vs. Feature**:
   - `common.json`: Truly shared strings (Yes/No, Cancel/Save, generic table headers, breadcrumbs)
   - Feature namespace: All feature-specific strings, even if duplicated

**Note**: When splitting large namespaces, update:
- `src/lib/i18n/config.ts` - register new namespaces
- `src/types/i18next.d.ts` - add type definitions
- Component imports: Change `useTranslation('oldNamespace')` to feature namespace

## AI Agent i18n Checklist (MANDATORY)

**Before completing any component work, AI MUST verify:**

- [ ] **Namespace derived correctly**: Use feature folder name as namespace (e.g., `features/students/` → `useTranslation('students')`)
- [ ] **No hardcoded strings**: Search component for patterns `["'][A-Z][a-z]{3,}.*["']` (exclude technical identifiers)
- [ ] **Translation keys exist**: All used keys must exist in both `en` and `vi` JSON files
- [ ] **Key structure follows pattern**: Use `{context}.{group}.{element}.{modifier}` (e.g., `form.fields.email.label`)
- [ ] **Standard template used**: New namespaces include required groups: `title`, `table`, `form`, `delete`, `status`, `actions`, `errors`
- [ ] **Placeholder text**: Form placeholders use `t('form.fields.{field}.placeholder')`, not hardcoded
- [ ] **Status labels**: Status badges use `t('status.active')`, not `"Active"`
- [ ] **Button text**: All buttons use `t('form.actions.create')` or `t('actions.edit')`, not hardcoded
- [ ] **Error messages**: Zod validation errors are automatically translated via Zod v4 locale system (configured in `src/lib/i18n/config.ts`). Only fallback messages need manual translation keys. Display errors inline below form inputs.

### Exception: Technical/Non-translatable Content

The following are **allowed** as hardcoded strings:
- **Technical identifiers**: `"ID"`, `"UUID"`, `"API"`
- **Symbols**: `"#"`, `"+"`, `"-"`, `"%"`
- **Code/classNames**: Tailwind classes, HTML attributes
- **Error codes**: `"ERR_404"`, `"INVALID_TOKEN"`

### Pattern Detection Examples

**❌ BAD - Will be flagged:**
```tsx
<Button>Submit</Button>
<p>No data found</p>
const status = user.isActive ? "Active" : "Inactive"
```

**✅ GOOD:**
```tsx
<Button>{t('form.submit')}</Button>
<p>{t('table.empty')}</p>
const status = user.isActive ? t('status.active') : t('status.inactive')
```

## Auto-Detection Strategy for AI

When AI generates or modifies a component:

1. **Scan phase**: After generating code, regex search for: `["'][A-Z][a-z]{3,}.*["']`
2. **Report phase**: List all detected hardcoded strings
3. **Fix phase**: For each match, either:
   - Add to appropriate JSON namespace + use `t()` call
   - Justify as exception (technical identifier)
4. **Verify phase**: Confirm all `t('key')` calls have corresponding JSON entries

## AI Quick Reference

When working with i18n, AI MUST:

1. **Derive namespace** from feature folder name: `features/{name}/` → `useTranslation('{name}')`
2. **Use standard template** when creating new namespaces (see template above)
3. **Follow key pattern**: `{context}.{group}.{element}.{modifier}` (e.g., `form.fields.email.label`)
4. **Check both locales**: Add keys to `en/` and `vi/` files
5. **Keep files under 200 lines**: Split large namespaces by feature domain

**Key Principle**: Never hardcode text. Always add translation keys first, then use them. TypeScript will catch invalid keys.
